SUPABASE AND IMAGE-GENERATION SETUP DISCUSSED
- The Supabase REST client appends `/rest/v1/...` and `/storage/v1/...` paths
  itself, so `SUPABASE_URL` must be the project root URL rather than a URL that
  already includes `/rest/v1`.
- The user confirmed running `supabase/generated-images.sql` in Supabase SQL
  Editor.
- Cloudflare settings are read from the server runtime as
  `ENABLE_IMAGE_GENERATION`, `CLOUDFLARE_ACCOUNT_ID`, and
  `CLOUDFLARE_API_TOKEN`. They must be available to the same process that runs
  the Next.js server. The token is raw (no `Bearer` prefix) and should have
  Account → Workers AI → Read permission.
- `.env.local` is local/ignored and was not included in this report. No token,
  Supabase key, or other credential value is included here.
- Runtime logs shared in chat showed one generated image stored successfully
  (`POST /api/image 201`) and served successfully (`GET /api/generated-images/…
  200`). Later image requests returned `429`.
- The current local rate-limit settings reported during troubleshooting are
  `IMAGE_RATE_LIMIT=3` per IP per hour and `IMAGE_DAILY_CAP=20`. The Studio
  requests three images for each generated set. Without Upstash, local limits
  use in-memory counters, which reset when the dev server process restarts.
